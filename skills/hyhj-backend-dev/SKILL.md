# HYHJ 后端开发

以现有项目为起点，完成可运行、可核验、可交接的后端变更。先明确事实与边界，再做最小完整实现；实现、数据落点和验证证据需要相互对应。

## 适用方式

- 延续项目语言、框架、目录、依赖与发布方式，用户要求改变时再评估迁移。
- 不把某个项目的目录结构、数据库隔离方式或消息中间件变成通用要求。
- 本 skill 独立可用，不要求安装其他 skill、插件或专用工具。
- 当前任务只需调研、方案或评审时，交付对应结果；不要自动开始实现。

## 1. 开工先建立可信上下文

阅读适用的仓库说明和本次需求，定位运行入口、构建清单、相关测试与部署方式。
沿一条真实链路确认：协议入口 → 校验/权限 → 业务用例 → 数据或外部服务 → 返回结果。

对来源分别标注：

- **当前事实**：当前代码、依赖清单、迁移、实际运行结果；注明基线和时间。
- **有效目标**：用户已确认且仍有效的需求、契约和决策，可能尚未实现。
- **旧提案**：已被取代、已废止、待确认或只属于历史项目的方案。

有冲突时，先判断是在描述现状还是规定目标，再按有效决策及其适用范围裁定。
汇总笔记不能覆盖明确的有效决定；运行结果也不能自动授权改变目标行为。
无法裁定且影响产品行为或数据所有权时，说明具体冲突并请求必要澄清。

## 2. 按变更风险决定深度

| 级别 | 常见任务 | 最低有用验证 |
|---|---|---|
| 轻量 | 注释、配置说明、局部且可逆的小改 | 定点核对；代码变更采用已有静态检查或相关测试 |
| 常规 | 用例、接口、查询或业务规则调整 | 核心正常/失败路径，受影响契约和必要集成 |
| 高影响 | 权限、数据迁移、并发状态或外部副作用 | 相关边界、失败/恢复及真实依赖验证，明确未验证范围 |

风险由数据和行为影响决定，不靠改动行数判断。
已有检查通过且未产生新疑点时，不重复全套测试；轻改不强制增加测试。

## 3. 明确实现边界

用简短说明确定输入输出、业务规则、数据所有者、失败语义和完成条件。
对于重构，列出必须保持的调用方可见行为及获准改变的部分。
优先复用现有能力；新增依赖或基础设施须能解决当前具体问题。
确定性的工程事项主动落定；有多个合理产品方向、重要数据归属变化或破坏性选择时再问。
沿用已有授权，不重复请求确认，也不由开发任务推导出未授权的部署、安装或对外发布。

## 4. 完成最小完整切片

- 协议入口负责协议处理、校验和结果转换，业务规则进入所属模块或应用服务。
- API、任务和工具入口复用业务用例，避免复制权限或状态变更逻辑。
- 每项业务事实有明确所有者；缓存、索引和客户端状态只承担已声明的作用。
- 根据真实边界组织代码；小型功能不为形式完整而增加空目录、抽象或事件系统。
- 改接口先保护契约；改数据同步考虑约束、并发、事务和版本化迁移。
- 对外部调用定义超时、取消、重试条件和不确定结果，不以重试掩盖未知副作用。
- 文件的元数据、对象内容、权限、处理结果和删除流程保持一致。
- 不吞异常、不记录凭据，错误和日志保留足以定位失败的上下文。

## 5. 用证据确认完成

先验证变更最关键的行为，再补充风险要求的契约、数据库或外部适配验证。
可用隔离替身测试业务分支，但需明确它验证了哪一层。
mock、内存存储、空返回和本地 fallback 不能证明真实集成或持久化已完成。
涉及持久化时，按风险核对实际写入、独立读取和失败状态；必要时验证重启后的结果。
环境或工具不可用时，继续完成可验证部分，精确说明缺口，不假报通过。

检查行为与说明是否一致：失败是否可定位，数据是否落到正确位置，取消是否留下可解释状态。
修复发现的问题后只重跑相关检查；新增疑点再扩大验证。

## 6. 交付可接手的结果

说明发生了什么变化、为什么需要，以及关键验证结果和实际边界。
启动命令以仓库已有入口为准，列明新增配置项但不暴露配置值。
涉及数据结构时，给出迁移执行方式、兼容影响和恢复或前向修复办法。
涉及异步和外部集成时，说明任务查询、失败排查和副作用不确定时的处理路径。
区分已实现、已验证、未验证和剩余工作，不把只存在文档中的能力列为交付。
仅在任务包含相应授权时执行提交、推送、部署或发布，并报告实际结果。
